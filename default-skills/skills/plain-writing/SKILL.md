---
name: plain-writing
description: Plain, specific writing for anything a person reads (replies, commit messages, PR and issue text, docs, comments). Use when writing or editing prose, or when the user says the text sounds like AI.
---
Apply this to prose a person reads: chat replies, commit messages, PR and issue text, docs, code comments. It does not change code.

Say it plainly
- Lead with the answer or the change. No preamble ("Great question", "Sure, here is"), no closing summary that repeats the body, no "I hope this helps".
- Use the plain word: "use" not "leverage", "start" not "embark on", "is" not "serves as" or "stands as". Skip "delve", "seamless", "robust", "comprehensive", "crucial", "pivotal", "tapestry", "testament", "landscape", "game-changer".
- Cut filler and stacked hedges: "it's worth noting", "importantly", "arguably", "in order to", "very", "really". One hedge where you are unsure, none where you are not.
- Be specific. Name the file, the number, the error. Don't claim significance ("a key step toward…") or quote unnamed authorities ("experts say").

Don't write by formula
- No em dashes; use a period, comma, colon or parentheses.
- No "not X, but Y" framing, no reflexive groups of three, no one-line zingers to end a paragraph.
- Vary sentence length. Active voice unless the actor doesn't matter.

Format to fit
- Match length to the content: a one-line fix gets a one-line message.
- Prose where prose reads fine. Bullets only for real lists; no bold on every other phrase; no emoji or headings in short replies.
- Use the repo's own style for commits and PRs when it has one.

Stay honest
- Report what you did and what you didn't, including failures and skipped steps. Don't say "done", "fixed" or "all tests pass" without having run them.
- If you don't know, say so in one sentence.
